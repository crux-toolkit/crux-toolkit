# Tech Stack

What Crux is built with today, the gaps that put scientific correctness at
risk, and the stack we commit to moving to. Facts reflect `master` @
`0f57aa531` (2026-10-30).

## Gaps that threaten scientific consistency

1. **No PR-time correctness gate.** PRs merge without anything building or
   testing them. Wrong numbers can land unnoticed.
2. **Smoke tests run on Ubuntu only.** Nothing checks cross-platform
   numeric consistency (mission invariant 2), even though three other
   platforms are built.
3. **No tolerance policy.** Expected-output comparisons are ad hoc. It isn't
   written down which columns must match exactly and which may differ by
   floating-point noise.
4. **Unit tests are orphaned.** They exist for one tool and aren't built
   by default.
5. **Test harness in Ruby/Cucumber/Perl.** That's a third and fourth
   language beside C++ and Python, which raises contributor friction (#670).
6. **Toolchain breakages.** The macro bug above, `-fpermissive` in the Comet
   patch (#735), removed-in-C++17 APIs such as `ptr_fun` (#398), missing
   `<memory>` includes (#417) and Apple Silicon build failures (#651).
7. **Slow CI.** Full dependency rebuilds on every run (#736) discourage
   running tests often.

## Target stack (commitments)

### 1. Golden-output oracle (highest priority)

- A Python (pytest) harness runs each Crux command on small committed
  inputs and compares against **golden outputs** in-repo.
- **Tolerance policy**, versioned in `test/golden/TOLERANCES.md` and
  enforced by the harness:
  - **Exact:** identifiers, sequences, modification strings, protein IDs,
    charges, ranks, counts, column names and order, row counts.
  - **Absolute 1e-6 Da:** masses (neutral and m/z). Golden runs therefore
    set `--mass-precision` high enough to resolve it (the default of 4
    decimals can't). Masses read from output written at a lower precision
    are compared within half a unit in the last written decimal, and
    within `z` times that when a neutral mass is rebuilt from a rounded
    m/z.
  - **Relative 1e-6:** scores (XCorr, E-value, Percolator scores).
  - **Exact rank-order + relative 1e-6:** q-values and PEPs.
  - Any looser tolerance needs a written per-column justification.
  - NaN/Inf anywhere is a failure unless that column explicitly allows it.
- **Invariant checks**, each scoped to the commands whose outputs contain
  the data it needs. An applicability matrix in `test/golden/INVARIANTS.md`
  maps each command to its invariants. A check reports `not-applicable`
  only when the matrix says so. If the matrix says a check applies but the
  output lacks the required columns, the check fails.

  | Invariant | Applies to (initial list) |
  |---|---|
  | Target/decoy feature symmetry | `make-pin`, `percolator`, `tide-search`, `comet` (decoy runs) |
  | Monotone q-values | `percolator`, `assign-confidence`, `diameter` |
  | Mass consistency (below) | every command that reports peptide or precursor masses |
  | Format equivalence (tsv/pepXML/mzIdentML/pin) | commands with more than one output format for the same results |

  Mass consistency is defined with explicit formulas, using
  monoisotopic or average masses to match the `isotopic-mass` setting.
  There are two separate checks, because the observed precursor and the
  sequence-derived peptide mass can legitimately differ by the search
  tolerance:
  - **Peptide mass** (calculated from the sequence): the reported peptide
    mass equals `M = Σ residue masses + H₂O + Σ modification deltas`
    (static and variable, terminal mods included).
  - **Spectrum mass** (observed): for charge `z`, the reported spectrum
    neutral mass `S` and precursor m/z agree as
    `m/z = (S + z · m_proton) / z`, with `m_proton = 1.007276 Da`.
  - Tolerances follow the policy above, including its rule for rounded
    output.
- **Reference agreement tests:** `crux comet` vs. standalone Comet and
  `crux percolator` vs. standalone Percolator at the pinned versions.
- Golden files are updated only by an explicit `--update-golden` run, and
  the PR description must explain the diff.

### 2. Unit tests in CI

- Wire `test/unit-tests` into the root build behind `-DCRUX_BUILD_TESTS=ON`.
  Run via `ctest`.
- Correct `test/unit-tests/README.md`, which still describes a PXD005590
  download the tests no longer use.
- Every bug fix adds a unit test at the lowest layer that reproduces it.
- Retire `test/cppunit-tests` once its cases have been ported.

### 3. Ruby/Perl → Python smoke tests (#670)

- Port the Cucumber features to pytest one command at a time. Run both
  suites until each port is shown to cover the same cases.
- Delete `crux-test.pl`, the dead `runall` and the Cucumber dependency at
  the end.

### 4. CI as the gatekeeper

- Fixes merge into **`develop`**, an integration branch created from
  `master`. A workflow merges `master` into it on every `master` push and
  runs the full build there. `develop` is promoted to `master` in reviewed
  batches, so a bad change can be reverted before it reaches a release.
- On every **PR**: build + unit tests + golden-output tests on all four
  platforms (ubuntu-22.04, macos-15, macos-15-intel, windows-2022), plus
  the existing release-notes check.
- Cache `ext/` builds keyed on the dependency pin hashes (#736).
- Rename `lint.yml` to reflect what it does, and add a real lint job once
  #322/#325 are done.

### 5. Targeted toolchain fixes (not a modernization)

Repo-wide modernization is a non-goal (see `mission.md`, Out of scope).
Toolchain changes are limited to what open issues need:

- Fix the `use_cxx14` macro so the declared standard matches the C++14
  flags actually in use. The language standard stays where it is.
- Fix the specific build breakages in #735 (`-fpermissive`), #398
  (`ptr_fun`), #417 (`unique_ptr` include) and #651 (Apple Silicon), with
  the smallest change that works.
- Moving to C++17, changing the ABI or PIE flags, upgrading the Docker base
  or bumping dependencies happens only if a specific issue cannot be fixed
  without it. That decision is recorded in the PR.
- Compilers to keep working: whatever the four CI runners provide today
  (ubuntu-22.04 GCC, macos-15 / macos-15-intel Apple Clang, MSVC 2022).

## Rules for dependencies

- **Build dependencies** (everything under `ext/` that is compiled into
  Crux) are pinned to an exact tag, commit or checksummed tarball. Bumping a
  pin is its own PR, with golden-output diffs reviewed and explained.
  - `USE_LATEST_PWIZ=ON` (default `OFF`) uses an unpinned ProteoWizard
    build. It is for local experiments only. Release builds and golden-output
    CI runs must use the pinned version, and CI asserts that it is `OFF`.
- **Test and CI tooling** (pip, gem, apt and Homebrew packages, GitHub
  Actions) doesn't affect Crux's scientific output, but it can change what
  the tests see. Today it is unpinned (`numpy`, `pandas`, `cucumber`,
  `rspec` in `main.yml` and `test.yml`). The new pytest harness (Phase 3)
  and PR CI (Phase 5) pin their tooling in a lock file. The legacy
  Cucumber jobs stay as they are until they are retired (#670); pinning
  them is not worth the churn.
- Patches to upstream tools live in `ext/patches` with a comment linking the
  upstream issue/PR. The aim is to upstream them and delete them.
